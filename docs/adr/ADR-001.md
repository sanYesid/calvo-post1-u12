# ADR-001: Capas simples para persistencia; el seam de notificacion ya cubre el proximo cambio conocido

## Estado: Aceptado — 2026-11-06

## Contexto
Tras integrar los patrones de comportamiento Chain of Responsibility (`CadenaValidadores`), Strategy (`CalculadoraReembolso`) y Observer (`ObservadorCambioEstado`) sobre el sistema de solicitudes de reembolso de gastos corporativos, corresponde evaluar una decisión arquitectónica de nivel superior: ¿el sistema completo debe migrar a una arquitectura Hexagonal estricta —introduciendo puertos e interfaces intermedias con sus respectivos adaptadores y mappers para todas las dependencias externas— o debe mantenerse en una arquitectura en capas simples?

El criterio técnico de referencia establece que una arquitectura Hexagonal completa se justifica en sistemas que sobrevivirán 3 años o más con cambios reales y previstos de infraestructura. Al contrastar este criterio con los datos concretos del proyecto en sus dos fronteras externas, el escenario es asimétrico:
1. **Persistencia:** Actualmente el sistema utiliza `RepositorioSolicitudesJpa` (Spring Data JPA) y no existe ningún plan ni requerimiento en el área de Finanzas para cambiar el motor de base de datos relacional ni migrar a otra tecnología de almacenamiento.
2. **Notificación e integración externa:** El área de Contabilidad anunció formalmente que el próximo trimestre integrará un sistema externo por API para programar el pago de las solicitudes aprobadas, y Finanzas planea agregar un suscriptor adicional hacia un panel interno de métricas en los próximos meses.

## Evaluación del criterio de la Guía (sección 6.2)
El criterio exige dos condiciones simultáneas: vida útil de 3 años o más **y** cambios de infraestructura. Aplicado con datos del proyecto:

| Condición | Persistencia | Notificación |
| :--- | :--- | :--- |
| Vida útil ≥ 3 años | Sí: el sistema reemplaza de forma permanente la hoja de cálculo de Finanzas; no es un prototipo. | Sí, por la misma razón. |
| Cambios de infraestructura reales y previstos | **No.** No hay plan de cambiar de motor. Además, pasar de H2 a otra base relacional (por ejemplo PostgreSQL) solo exige cambiar la dependencia del driver y `application.properties`, porque `JpaRepository` ya abstrae el motor sin tocar `SolicitudReembolsoService`. | **Sí.** Hay dos cambios con fecha: la API de pagos de Contabilidad (próximo trimestre) y el panel de métricas (próximos meses). |
| ¿Se cumple el criterio? | **No** → no se justifica un puerto. | **Sí** → se necesita un punto de extensión; se verifica si el actual ya lo cubre. |

## Alternativas consideradas
| Alternativa | Qué implicaba | Por qué no se eligió |
| :--- | :--- | :--- |
| **A. Hexagonal completa** | Puerto `RepositorioSolicitudes` + `AdaptadorRepositorioJpa` + entidad JPA separada y mapper hacia el dominio; puerto `PublicadorCambioEstado` para notificaciones. | Agrega al menos 4 tipos nuevos en persistencia sin ningún cambio de motor previsto (**YAGNI**). En notificación duplicaría un puerto que ya existe (`ObservadorCambioEstado`). |
| **B. Hexagonal solo en notificación** | Puerto `ClientePagosContabilidad` en `procesamiento` con un adaptador HTTP en `infraestructura`, consumido por `NotificadorContabilidad`. | `ObservadorCambioEstado` ya cumple el rol de puerto de salida: la llamada a la API externa queda encapsulada dentro de `NotificadorContabilidad`. Una segunda interfaz sin una segunda implementación no supera el **test de explicabilidad**. Se reconsiderará si aparece un segundo consumidor de esa API. |
| **C. Capas simples + seam Observer (elegida)** | `SolicitudReembolsoService` → `RepositorioSolicitudesJpa` directo; notificación por `List<ObservadorCambioEstado>`. | Cubre los dos cambios conocidos sin abstracciones especulativas (**KISS**). |

## Decision
Se toma una decisión diferenciada por frontera según la evidencia real de cambio (alternativa C):

1. **Para la persistencia (Mantener Capas Simples):** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin introducir una interfaz de puerto intermedia `RepositorioSolicitudes` ni un adaptador JPA separado. Introducir hoy un puerto de persistencia con clases de mapeo adicionales sería una abstracción especulativa que viola el principio **YAGNI** (*You Aren't Gonna Need It*), ya que no existe ningún caso de uso ni cambio de motor de base de datos planeado que lo justifique, y `JpaRepository` ya provee el contrato necesario para pruebas e inversión de control en Spring.
2. **Para la notificación (Conservar el seam actual sin capas adicionales):** No se introduce ningún cambio estructural adicional en el paquete `procesamiento.notificacion`. La interfaz `ObservadorCambioEstado` implementada con el patrón **Observer** ya constituye el punto de extensión (*seam*) exacto que el sistema necesita:
   * Cuando Contabilidad integre la API externa el próximo trimestre, únicamente se actualizará la implementación interna de `NotificadorContabilidad` (o se inyectará un cliente HTTP dentro de ella) sin modificar una sola línea de `SolicitudReembolsoService` ni de los demás observadores.
   * Cuando Finanzas incorpore el panel interno de métricas, bastará con crear una nueva clase `@Component` que implemente `ObservadorCambioEstado` y Spring la suscribirá automáticamente.

## Consecuencias

### Positivas:
- **Cumplimiento de YAGNI y KISS en persistencia:** Se evita duplicar interfaces (`RepositorioSolicitudes` + `RepositorioSolicitudesJpa` + adaptador + mapper de entidades) sin un conductor de negocio real que lo respalde hoy.
- **Preparación real ante el cambio confirmado en notificaciones:** El único cambio de infraestructura con fecha conocida (integración de Contabilidad con API externa el próximo trimestre y futuro panel de métricas) ya cuenta con su punto de extensión desacoplado a través de `ObservadorCambioEstado`.
- **Aislamiento de la lógica de negocio:** El paquete `procesamiento` (`validacion`, `calculo`, `notificacion`) permanece 100% libre de dependencias hacia `RepositorioSolicitudesJpa` o clases de acceso a datos, dado que `SolicitudReembolsoService` carga previamente las solicitudes pendientes y las entrega como una colección en memoria. Este límite se verifica automáticamente con la Regla 1 de ArchUnit (`procesamientoSinPersistenciaNiWeb`).

### Negativas:
- **Deuda técnica consciente ante un eventual cambio no previsto de base de datos:** Si en el futuro surgiera la necesidad de reemplazar JPA por un motor no soportado por Spring Data JPA, el puerto de persistencia deberá extraerse mediante refactorización retroactiva en ese momento. Se acepta este costo conscientemente porque su probabilidad actual es nula.
- **Asimetría intencional entre fronteras:** Un revisor externo que espere simetría arquitectónica total (puertos explícitos en absolutamente todas las dependencias) podría interpretar la ausencia de un puerto de persistencia como una omisión si no consulta este ADR.
- **`NotificadorContabilidad` asumirá una dependencia HTTP:** Al integrar la API externa, ese observador dependerá de un cliente HTTP y será más difícil de probar en aislamiento; se mitigará inyectando el cliente por constructor para poder sustituirlo en pruebas.

## Señales que harían revisar esta decisión
- Un requerimiento formal de cambiar a un motor no relacional o a un servicio de almacenamiento externo.
- Un segundo consumidor de la API de pagos de Contabilidad, distinto de `NotificadorContabilidad`.
